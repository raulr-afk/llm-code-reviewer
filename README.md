A small, dependency-free tool that compares **two Python solutions** to the same
problem (for example, two answers generated by different LLMs) and produces a
structured review covering **correctness**, **efficiency** and **readability**.

It is built around the kind of evaluation work done when reviewing AI-generated code:
run it, test it against edge cases, measure it, and justify the verdict.

## Features

- **Sandboxed execution**: each solution runs in its own subprocess, so crashes,
  infinite loops and stray `print` calls cannot affect the reviewer.
- **Per-test timeouts** and clear failure messages (wrong answer, exception, timeout).
- **Static analysis** with the stdlib `ast`: cyclomatic complexity, nesting depth,
  loop depth (a hint for O(n^2)/O(n^3) behaviour), docstrings, type hints, naming.
- **Transparent scoring** with documented weights, no black box.
- Reports in **Markdown** or **JSON**.
- No runtime dependencies. Python 3.9+.

## Install

```bash
git clone https://github.com/YOUR_USERNAME/llm-code-reviewer.git
cd llm-code-reviewer
pip install -e ".[dev]"
```

## Usage

```bash
code-reviewer examples/problem.json examples/solution_a.py examples/solution_b.py
code-reviewer examples/problem.json examples/solution_a.py examples/solution_b.py -f json -o report.json
```

A problem is a JSON file:

```json
{
  "title": "Longest substring without repeating characters",
  "function_name": "longest_unique_substring",
  "description": "Return the length of the longest substring with no repeated characters.",
  "timeout": 5,
  "tests": [
    {"name": "empty", "args": [""], "expected": 0},
    {"name": "classic", "args": ["abcabcbb"], "expected": 3}
  ]
}
```

`args` is the list of positional arguments, `expected` the exact return value
(JSON-serialisable). `timeout` is in seconds, per test.

Sample output (see [`examples/sample_report.md`](examples/sample_report.md)):

| Criterion | Weight | A (brute force) | B (sliding window) |
|---|---|---|---|
| Correctness | 60% | 100.0 | 100.0 |
| Efficiency | 20% | 0.1 | 100.0 |
| Readability | 20% | 85.0 | 100.0 |
| **Overall** | | **77.0** | **100.0** |

Use it as a library too:

```python
from code_reviewer import Problem, compare

review = compare(Problem.from_file("examples/problem.json"),
                 "examples/solution_a.py", "examples/solution_b.py")
print(review.verdict, review.a.scores, review.b.scores)
```

## How scoring works

| Criterion | Weight | How it is computed |
|---|---|---|
| Correctness | 60% | Share of tests passed |
| Efficiency | 20% | Runtime on tests **both** solutions passed, relative to the faster one. Differences under 20% or under 50 ms total are treated as noise. A solution passing nothing gets 0. |
| Readability | 20% | Starts at 100; penalties for high complexity (>10), deep nesting (>3), missing docstring, missing type hints, many cryptic names, very long lines |

The verdict is a tie if overall scores differ by less than 2 points.

### Limitations (by design)

- Readability is a heuristic. It cannot judge whether code is *clear*, only flag common smells.
- Efficiency is measured empirically on your test inputs: include a large input to
  expose bad algorithmic complexity.
- Process isolation protects against crashes and hangs but is **not a security sandbox**.
  Do not run untrusted code on a machine you care about; use a container.
- Timeouts rely on `SIGALRM` (Linux/macOS). On Windows only the global backstop timeout applies.

## Project layout

```
src/code_reviewer/
  models.py     dataclasses (Problem, TestCase, results, metrics)
  _harness.py   child-process test executor
  runner.py     launches the harness, handles crashes/timeouts
  metrics.py    AST-based static analysis + readability score
  reviewer.py   scoring and verdict
  report.py     Markdown / JSON output
  cli.py        command line entry point
tests/          pytest suite
examples/       sample problem, two solutions, generated report
```
